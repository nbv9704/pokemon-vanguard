# B29 — Admin overview accuracy, summary-only reads and stable campaign pagination (#28)

## Population and contract

`/api/admin/overview` now covers the complete storage population (all `profiles` in cloud, all eligible local save files in local beta), **not** the first 100 account saves. `online` always comes from the live registry and is a separate, process-local measurement, not a database aggregate. `aggregateScope='all'` and `sampledAccounts=players` describe the actual database/JSON scan scope. A profile without a cloud save contributes zero currency, unsuspended and default Poké Ball rank. Aggregate totals/tiers from the cloud database are computed in one read-only, service-role-only SQL statement. They are current at query time; concurrent writes can change numbers between two dashboard refreshes.

Cloud `/api/admin/players` calls `admin_account_page`: the RPC transfers **only** reviewed scalar, wallet/ticket/rank/count metrics and public profile metadata, never `game_saves.state`, receipts, chat, tokens or audit. Full game state remains available **only** for explicit selected-player details and authorized mutations. UI list uses immutable `user_id` order instead of mutable `updated_at`, allowing stable offset pages when only update timestamps change; `Load more` is available after the first 50 results.

## Gift audience and long requests

`admin_gift_audience_page` uses immutable UUID **keyset** pagination of at most 250 IDs per SQL request, optionally filtering rank using exactly the five current thresholds. Local JSON follows sorted stable IDs. The server collects ID strings only (up to a guarded 50,000), freezes them into the existing immutable/idempotent manifest **before** delivery, and reuses that snapshot on retries. Account state is loaded only for the currently processed recipients. One HTTP gift request delivers at most **100 recipients** with up to 12 concurrent account locks. For a larger campaign, the response includes `nextCursor` and `remaining`; the Admin UI persists the same campaign plus cursor in session storage and requires explicit continuation. When a batch has failures, it preserves its cursor and repeats that batch on retry; the durable per-account receipt safely deduplicates already-committed gifts after lost ACK/restart. Invalid cursors are rejected without writes.

**Caution:** building a 50k-ID audience still consumes CPU and JSON storage for the immutable campaign manifest. The endpoint intentionally avoids 50k full-save objects or synchronous 50k-recipient writes, but it is **not** a fully backgrounded campaign worker. Each page is a separate read: simultaneous profile insertions or rank changes across pages are not a database-wide serializable snapshot. If strict time-of-request membership is required, migrate manifest capture to a single transaction / server-owned job; do not silently label these paginated reads a database snapshot.
