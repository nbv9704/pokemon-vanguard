# B07 — Authenticated socket lifetime, PvE retry receipts, detached-room reclamation

## Scope

- **Authenticated sessions:** every newly issued session has an unpredictable session ID and a seven-day expiry. The signed cookie is validated on HTTP read, WebSocket upgrade, WebSocket connect, and at the start of each queued message. WebSocket connections also receive an expiry deadline. Logout revokes the current signed session ID and closes its joined or still-joining sockets in **the same server process** with terminal code `4001`. Legacy signed cookies without a session ID receive a stable token-derived ID until they expire; this preserves existing player IDs and saves. Cloud sessions require an allowed provider and consistent UUID/account/room mapping. Local Beta retains 128-character legacy player IDs; the WebSocket room route allows the corresponding 135-character `aether-` prefix.
- **Bounded sockets:** `createLocalServer()` accepts `websocketJoinDeadlineMs` (default 12 seconds) and `maxSocketsPerAccount` (default four, clamped between 1 and 16). A connection waiting for its first `join` counts toward this limit. An account cannot bypass the cap simply by opening sockets without joining.
- **Schema-3 PvE:** actions with an `actionId` use a SHA-256 fingerprint over the canonical action payload. Receipt validation takes place **before** phase/revision validation, so retrying an already committed move after a lost ACK cannot resolve the turn again. The receipt is stored in the same player save as the resulting battle and any mission/reward effects. The server reloads the durable save on retry, broadcasts committed state, then sends `action-ack` with its action ID. Using the same ID with a different payload fails `ACTION_ID_REUSED`. Legacy no-ID battle actions remain compatible but do not receive cross-restart dedupe.
- **Client:** Shop, Recruitment and PvE share one explicit-retry outbox per account/tab in `sessionStorage`. A new operation is blocked while another is awaiting ACK. On reload/reconnect, the player decides whether to retry the *same* payload and ID or discard the local retry option; there is **no automatic battle replay**. Missing or blocked session storage remains a durability limitation for the client.
- **Detached rooms:** `createLocalServer()` accepts `roomRetentionMs` (default 10 minutes). At most once a minute, idle rooms are reclaimed only if all sockets have left, no join is pending, the serial queue is empty, the retention period has passed, and neither Ranked nor Friendly owns an active reference. Associated in-process presence is dropped. A later visit reloads the durable save rather than recreating player progress.

## Remaining work

1. Session revocation is **per process**. Revoked token IDs currently have no cross-process or restart-persistent store. In-flight commands that entered the account queue before the exact moment of expiry still need a cancellation/commit-boundary policy. Supabase session rules remain to be exercised against real auth/DB.
2. Active Ranked/Friendly matches and decision timers are still **not restored after process restart**; only previously committed Ranked results are recovered. Before implementing live rehydration, design a coherent two-account snapshot and a single authoritative match owner, then fault-test crash/timeout races.
3. Receipt storage remains unbounded until an archival deduplication strategy exists; do not delete old IDs merely to shrink saves. Per-IP quotas, distributed socket limits and soak tests remain outstanding.
